i)  ADMIN SIGN-IN – AUTHENTICATION AND AUTHORISATION
----------------------------------------------------------------

THEORY:
Authentication is the process of verifying the identity of a
user, while Authorisation determines what resources or actions
that verified user is permitted to access.

In NovaCart, a token-based authentication strategy using
JSON Web Tokens (JWT) has been implemented.

How It Works:
1. The admin submits their email and password via the
   Admin Login page (/admin/login).

2. The backend (authController.js) receives the credentials,
   finds the user in MongoDB, and uses bcryptjs to compare
   the hashed password stored in the database with the
   submitted password.

3. If credentials are valid AND the user's role is "admin",
   a signed JWT token is generated using jwt.sign() with a
   7-day expiry and returned to the client.

4. The frontend stores this token in localStorage and attaches
   it to all subsequent HTTP requests as a Bearer token in
   the Authorization header.

5. On the backend, every protected admin route passes through
   the `protect` middleware (which verifies the JWT) and the
   `adminOnly` middleware (which checks role === 'admin').
   Unauthorized users receive a 401/403 HTTP response.

Key Concepts:
- Hashing      : Passwords are never stored in plain text.
                 bcrypt.genSalt() + bcrypt.hash() are used.
- JWT          : A stateless, self-contained token that carries
                 user identity and role information.
- Middleware   : Express middleware functions intercept requests
                 before they reach controllers, enabling
                 centralised security enforcement.
- Role-Based   : Users have roles ('user' or 'admin'). Only
  Access Control  admin-role accounts can access dashboard routes.

ii) PRODUCT MANAGEMENT (CRUD) – DASHBOARD TO FRONT-END SYNC
----------------------------------------------------------------

THEORY:
CRUD stands for Create, Read, Update, and Delete — the four
fundamental operations performed on any data resource. In a
full-stack application, the Admin Dashboard acts as the data
management layer, and any changes made there are persisted
to the shared MongoDB database, ensuring they are immediately
visible on the customer-facing frontend.

Implementation in NovaCart:

CREATE  – Admin fills the "Add Product" form in the dashboard.
          A multipart/form-data request (supporting image upload
          via Multer middleware) is sent to POST /api/products.
          The new product document is saved in MongoDB.

READ    – The shop page (Shop.jsx) fetches GET /api/products
          on load. Products are returned from MongoDB and
          rendered as cards with category filters and search.

UPDATE  – Admin clicks "Edit" on any product, modifies the
          fields, and submits. A PUT /api/products/:id request
          updates the document in MongoDB. The next time any
          user visits the shop, the updated data is shown.

DELETE  – Admin clicks "Delete". A DELETE /api/products/:id
          request removes the document from MongoDB. The product
          disappears from the storefront immediately on refresh.

Image Handling:
Product images are uploaded to the server using Multer
(stored in /backend/uploads/). The image path is saved in
MongoDB and served as a static URL (/uploads/filename.jpg)
so the frontend can display it via a standard <img> tag.

Why Changes Reflect Immediately:
Since both the admin dashboard and the customer storefront
read from and write to the same MongoDB database, there is a
single source of truth. No caching layer exists, so every API
call returns the latest data directly from the database.

iii) SEO TAGS, DESCRIPTION AND META DETAILS ON PRODUCT PAGE
----------------------------------------------------------------

THEORY:
Search Engine Optimisation (SEO) is the practice of improving
a website's visibility on search engine results pages (SERPs).
For an e-commerce store, per-product SEO is critical because
each product page can rank independently for specific keywords.

Meta Tags and Their Purpose:
- <title>          : The clickable headline shown in search
                     results. Should be 50–60 characters.
- <meta description>: A 150–160 character summary displayed
                     under the title in search results. Does
                     not affect ranking directly but improves
                     click-through rate (CTR).
- <meta keywords>  : Comma-separated terms relevant to the
                     product (less weighted by Google but still
                     used by some search engines).
- URL Slug         : A human-readable, keyword-rich URL segment
                     (e.g., /product/fresh-organic-tomatoes)
                     that helps search engines understand the
                     page topic.

Implementation in NovaCart:
The Product model (MongoDB Schema) includes dedicated fields:
  - description
  - slug
  - metaTitle
  - metaDescription
  - metaKeywords

Admin sets these values per product from the dashboard
Products form. On the product detail page (ProductDetail.jsx),
the react-helmet-async library is used to dynamically inject
these values into the HTML <head> of the page:

  <Helmet>
    <title>{product.metaTitle}</title>
    <meta name="description" content={product.metaDescription} />
    <meta name="keywords" content={product.metaKeywords} />
  </Helmet>

This ensures each product page has unique, admin-controlled
SEO metadata, which is essential for organic search traffic.

The slug field enables clean, SEO-friendly URLs:
  /product/fresh-organic-tomatoes
instead of:
  /product/64f3abc12d...  (MongoDB ObjectId)

Products are fetched by slug via GET /api/products/slug/:slug.

iv) CART AND CHECKOUT – SANDBOX DEPLOYMENT
----------------------------------------------------------------

THEORY:
The shopping cart and checkout process are the core transactional
components of any e-commerce application. They must be reliable,
secure, and provide a smooth user experience.

Cart Implementation:
The cart is managed through a React Context (CartContext.jsx)
which provides global cart state to all components.

- For logged-in users  : Cart data is synced with the backend
                         (stored in the User document in MongoDB
                         as an embedded array). On login, the
                         server-side cart is loaded.
- For guest users      : Cart is persisted in localStorage so
                         items survive page refreshes.

Cart operations supported:
  addToCart()     – Adds an item or increments quantity
  removeFromCart() – Removes an item by product ID
  updateQty()     – Changes quantity (removes if qty = 0)
  clearCart()     – Empties the cart after order placement

Checkout Process:
1. User navigates to /checkout (protected route — login required)
2. User fills in the shipping address form (name, street, city,
   province, postal code, country).
3. Payment Method: Cash on Delivery (COD) is implemented as the
   primary sandbox payment method. This eliminates the need for
   real payment gateway credentials during development/testing.
4. On form submission, a POST /api/orders request is sent with:
   - All cart items (product ID, name, price, quantity, image)
   - Shipping address
   - Subtotal, delivery fee, and total amounts
5. The Order document is created in MongoDB with status "processing"
6. Cart is cleared and user is redirected to the order detail
   page with a success confirmation message.

Sandbox Note:
The system is fully functional in a local/sandbox environment.
Cash on Delivery is used as the payment sandbox, representing
a complete checkout flow without requiring live payment keys.
Stripe integration is prepared in the backend (stripe package
installed, STRIPE_SECRET_KEY in .env) for future production use.

Order Status Flow:
  processing → confirmed → shipped → delivered
  (Each stage can be updated by admin from Admin Orders page)

v)  USER MANAGEMENT – SIGNIN, SIGNUP, CART, WISHLIST,
    ORDER MANAGEMENT AND TRACKING
----------------------------------------------------------------

THEORY:
User management encompasses all functionality related to
individual customer accounts — from registration to post-purchase
order tracking. A well-implemented user system enhances
personalisation, security, and customer retention.

1. SIGN UP (Registration):
   Users register via POST /api/auth/register with name, email,
   and password. The password is hashed using bcryptjs before
   storage. A JWT token is returned on successful registration,
   logging the user in immediately. Duplicate email addresses
   are rejected with a 400 error.

2. SIGN IN (Login):
   Users authenticate via POST /api/auth/login. The backend
   verifies the email exists, then uses bcrypt.compare() to
   validate the password. On success, a JWT token is issued.
   The frontend stores this token in localStorage and uses it
   for all subsequent authenticated API calls via the api.js
   utility (which auto-attaches the Bearer token header).

3. CART (Persistent, Synced):
   As described in section iv, the cart state is:
   - Stored server-side for logged-in users (MongoDB User doc)
   - Stored in localStorage for guests
   This ensures cart items persist across sessions and devices.

4. WISHLIST:
   The wishlist is managed via WishlistContext.jsx. It calls:
   - POST /api/users/wishlist/add     – to save a product
   - POST /api/users/wishlist/remove  – to remove a product
   - GET  /api/users/wishlist         – to load saved items
   The wishlist page (/wishlist) displays saved products with
   the option to add them directly to cart or remove them.
   Unauthenticated users are redirected to the login page.

5. ORDER MANAGEMENT:
   After checkout, orders are stored in MongoDB with:
   - Full item list (name, price, quantity, image)
   - Shipping address
   - Total amounts
   - Status: processing / confirmed / shipped / delivered / cancelled
   - Timestamps (createdAt, updatedAt)

   Customers view all their past orders at /orders (fetched
   via GET /api/orders/mine — returns only the logged-in user's
   orders using their JWT identity).

6. ORDER TRACKING:
   Each order has a detail page at /orders/:id which shows:
   - A visual step-by-step progress tracker (Processing →
     Confirmed → Shipped → Delivered)
   - Shipping address details
   - Itemised list of ordered products with images
   - Order total and date

   Admin can update the order status from the Admin Orders
   page using a dropdown. When the status changes in MongoDB,
   the customer sees the updated status the next time they
   view their order detail page — completing the full
   order-tracking cycle.

7. ROUTE PROTECTION:
   All user-specific routes (/checkout, /orders, /wishlist)
   are wrapped with a ProtectedRoute component that checks for
   a valid JWT in localStorage. If no token exists, the user is
   redirected to /login before they can access the page.
